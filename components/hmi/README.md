# hmi

The user interface: the EEZ Studio / LVGL project and the C "bridge" that wires
it to the services.

## What it does

Owns everything on the 800×480 touch screen. It has two halves:

- **`src/ui/`** — generated LVGL code. It comes from the EEZ Studio project
  (`OBD_Dash.eez-project`) via `tools/eez-build.sh`; **do not hand-edit** these
  files, they are overwritten on every UI build.
- **`bridge/`** — hand-written C that reads the services and drives the UI
  (and vice versa). This is where OBD_Dash logic meets the widgets.

## Dependencies

`lvgl` (public); `board`, and almost every service: `comsm`, `obd`,
`vehicle_data`, `settings`, `datalog`, `can_if`, `canmon`, `io_svc`,
`wifi_svc`, `ble_svc`, `web_svc`, `dash_svc`, `diagdb` (private). The HMI sits
at the **top** of the stack and depends on everything; nothing depends on it.

## Threading

**Everything in `bridge/` runs in the LVGL task** (lv_timers, event callbacks,
EEZ native actions). The EEZ flow engine is not thread safe, so the bridge
reaches services only through their own thread-safe APIs, and never blocks on
the bus (that's comsm's job).

## Integration

The board's LVGL port calls two hooks (set in `main.c` via
`lvgl_port_set_ui_hooks`):

```c
hmi_init();     /* build screens, restore the last page, start the UI timers */
hmi_tick();     /* periodic UI refresh from service status snapshots */
```

## How the bridge reaches the EEZ project

Two mechanisms (see [bridge/bridge.h](bridge/bridge.h)):

1. **By name** (`uivar.c` / `nav.c`) — the menu/sidebar pages generated by
   `tools/obd_ui.py`. A variable missing from the UI is silently ignored, so
   the C and the EEZ project can evolve a little independently.

   ```c
   static uivar_t v_rpm = UIVAR("obd_rpm");
   uv_strf(&v_rpm, "%.0f", rpm);        /* only redraws if the text changed */
   nav_go("dash");                       /* switch page by EEZ screen name */
   ```

2. **By generated enum / `objects.*`** (`vars.h`, `screens.h`) — the live views
   and the OBD controllers that predate the name mechanism (`ui_bridge`,
   `live_*`, `diag_view`, `pid_select_view`).

## File map (`bridge/`)

| File | Page / role |
|---|---|
| `hmi.c` | init, tick, top-level wiring |
| `nav.c`, `uivar.c`, `screen.c`, `ui_bridge.c` | navigation + EEZ access helpers |
| `live_view.c`, `live_values.c` | live gauges / race view |
| `view_obd.c`, `diag_view.c`, `pid_select_view.c` | OBD connect, DTCs, PID selection |
| `view_dash.c` | Dash page (DBC tiles, limits) |
| `view_diag.c` | Diag page (UDS scan, identify, DTCs, report) |
| `view_link.c`, `view_elm.c` | car interface (board CAN / BLE adapter) |
| `view_can.c` | CAN monitor page |
| `view_wifi.c`, `view_ble.c`, `view_io.c`, `view_sys.c` | Wi-Fi, BLE, IO, system pages |
| `brightness.c`, `actions.c`, `nav.c` | misc EEZ native actions |

## Editing the UI

Keep the **EEZ project the source of truth**. Menu pages are generated by
`tools/obd_ui.py`; after changing them (or the EEZ project), regenerate:

```sh
python3 tools/obd_ui.py          # regenerate the EEZ project pages
tools/eez-build.sh               # regenerate components/hmi/src/ui/ from the project
```

See the top-level [CLAUDE.md](../../CLAUDE.md) for the EEZ headless-build
details and gotchas.

## Gotchas

- Never edit `src/ui/*` by hand — run the UI build instead.
- `OBD_Dash.eez-project-ui-state` is the owner's local editor state and is
  **not** committed.
- Bridge code must stay non-blocking: read a service's status snapshot, update
  widgets, return. Long or bus-bound work belongs in a service task.
- Sidebar buttons are one line (icon + name) at a 46 px pitch to fit the page —
  keep new entries within that.
