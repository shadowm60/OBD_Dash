# OBD_Dash: context for Claude Code sessions

Read this first, then `README.md` (architecture, live screen field/PID tables, logging,
roadmap). This file holds what the README doesn't: how to work in the repo, the
gotchas, and where development stopped.

## Project

An OBD-II dashboard on a **Waveshare ESP32-S3-Touch-LCD-5**: 800x480 RGB panel, GT911
touch, CH422G IO expander, SD card, and TWAI (CAN) at 500 kbit/s.

- **Software:** ESP-IDF v6.1, LVGL 8.3, and a UI designed in EEZ Studio 0.29 using EEZ Flow
  (`EEZ_FOR_LVGL`).
- **Test setup:** on the bench, a Python car simulator on a PC with a second ESP32 as
  the CAN interface. Since 2026-11-11 also in the owner's car, with SD card logs
  (`ObdDash_Logs/`, not committed). The car's bus is busy, unlike the bench.
- **Owner:** shadowm60. Their English is informal; read requests for intent.

## Build / flash / UI

```sh
. ~/.espressif/tools/activate_idf_v6.1.sh
ninja -C build                      # normal build
idf.py -B build reconfigure         # after Kconfig / sdkconfig.defaults changes
idf.py -B build flash monitor       # owner usually flashes himself
tools/eez-build.sh                  # regenerate components/hmi/src/ui/ from the EEZ project
```

- **ninja warning:** the VS Code ninja is a different version. A "build log version"
  warning just means a full rebuild.
- **`sdkconfig` is the owner's local file** and is not committed. Put defaults in
  `sdkconfig.defaults`, and mirror needed changes into `sdkconfig` by hand.
- **EEZ headless build:** EEZ Studio is at `~/tools/EEZ-Studio-0.29.0.AppImage`, and the
  script handles its quirks: unset `ELECTRON_RUN_AS_NODE`, `--no-sandbox --disable-gpu
  --ozone-platform=x11`, `APPIMAGE_EXTRACT_AND_RUN=1`. It should print "No error and no
  warning detected" / "Build successfully finished".

## Editing the UI: keep the EEZ project the source of truth

**Menu pages** (sidebar pages, see README "Pages") are generated by
`tools/obd_ui.py` into the project: change the builders there, run it, then
`tools/eez-build.sh`. EEZ Studio edits to those pages are overwritten by the next
run. Their variables, actions and screens are reached **by name** from C
(`bridge/uivar.c`, `nav.c`, `actions.c`). The live views (drive / liveData / tune)
are only edited in EEZ Studio, as described below.

The owner opens `components/hmi/OBD_Dash.eez-project` in EEZ Studio. Treat it as
follows:

1. **Never hand-edit `components/hmi/src/ui/*`.** It is generated.
2. **Change layout by editing the project JSON** with a short Python script. Do it the
   way EEZ stores it:
   - 2-space indent, `ensure_ascii=False`.
   - Fresh UUID `objID`s for cloned widgets.
   - When cloning a widget, drop its `eventHandlers` unless an action really exists.
   - Then run `tools/eez-build.sh`, then `ninja -C build`.
3. **Widgets that C code touches need an `identifier`.** They then appear as
   `objects.<identifier>` in `screens.h`.
4. **Do not commit `OBD_Dash.eez-project-ui-state`.** It is the owner's editor state.

Screens (`ScreensEnum`, order set by `ORDER` in `tools/obd_ui.py`):

| Screen | Purpose |
|---|---|
| home | Home (first screen at the very first boot) |
| obd | OBD scanner: connect, live views, options |
| readDTC | trouble codes (read / clear / save) |
| select_params | OBD > Select parameters (list built by pid_select_view into `obd_srv_table`) |
| freezFrame | freeze frame (text built by diag_view into `ff_panel`) |
| drive / liveData / tune | full-screen live views (Drive / Race / Tune), EEZ Studio only |
| can, wifi, ble, io, display | menu pages |

Navigation:
- Always `nav_go(name)` / `nav_go_anim(...)` (`bridge/nav.c`): it stores the page so
  it comes back at power-up. Don't call `eez_flow_set_screen` directly.
  `loadScreen` does not exist in this build.
- Live screens: swipe left/right to cycle Drive -> Race -> Tune; swipe up/down or long
  press to go to the OBD page (`live_view.c`).

## Architecture rules (see README for the component list)

**Layering.** The layers, bottom to top:

| Layer | Role |
|---|---|
| `can_if` | TWAI driver |
| `isotp` | ISO-TP transport |
| `obd` | client, PID catalogue/scheduler, DTC |
| `comsm` | connection state machine, single task |
| `vehicle_data` | thread-safe signal store |
| `hmi/bridge` | the only code touching LVGL/EEZ, runs in LVGL timers |
| `settings` | NVS blob |
| `datalog` | SD card logging |

Producers never call LVGL.

**PID catalogue** (`obd/obd_pid_table.c`):
- Each entry is pid, data length, rate, signal and decoder.
- Rates: FAST is round-robin, MEDIUM is 500 ms, SLOW is 2000 ms.
- Polling is opt-in. Only PIDs that are selected in Select Params AND supported by the
  ECU are polled.

**Multi-PID polling:**
- Up to 6 PIDs are requested per Service 01 request (`obd_pid_next_batch`). Due timed
  PIDs get at most half the slots.
- comsm falls back to 1 PID per request if the ECU rejects a batch.
- The batch size is set with `comsm_set_pids_per_request` (System > Read speed).

**Settings blob** (`settings.c`):
- Versioned (`SETTINGS_VER`).
- **New fields go at the end of `app_settings_t`.** A shorter blob of the same version
  still loads, and new fields keep their defaults.
- Bump the version only for incompatible changes, because that wipes the owner's
  settings (PID selection).

**Displaying values:**
- **Text tiles:** EEZ string vars `v_*`, formatted in `live_values.c`.
  - Shows `--` when the value is invalid or older than 10 s.
  - Disconnect and deselect invalidate values immediately.
- **Needles:** int vars `rpm_value` and `afr_value` (AFR x100), via `ui_bridge.c`
  bindings.
  - Animated linearly over the measured sample interval. This can be switched off at
    System > Gauge animation.
- **Gauge scaling** (`live_view.c`): lv_meter is integer-only. Gauges run in raw units
  and their tick labels are rewritten.
  - drive_rpm_gauge: x1000
  - rpm_gauge: x100
  - afr_gauge: x`AFR_GAUGE_SCALE` (100)

**Performance:**
- Meter backgrounds are baked once into an `lv_snapshot` image (`bake_background`).
- Labels lying fully inside a meter get frozen into that image. Live values on a gauge
  must therefore sit inside a panel (tile).
- Display: direct mode, avoid-tear mode 3, ~39 Hz vsync, `LV_DISP_DEF_REFR_PERIOD=15`.

**OBD:**
- The default diagnostic session needs **no** Tester Present.
- The idle keepalive (`CONFIG_OBD_KEEPALIVE_MS`) is off by default. The owner does not
  want periodic `01 00` while idle.

## Working conventions

- **Branch:** `restructure`, with PRs to `main`.
- **Commits:** commit when a task is finished and builds, as has been done throughout.
  - Use short messages with a prefix, e.g. `hmi:`, `obd:`, `comsm:`, `readme:`.
  - End each message with the Co-Authored-By line from the session's instructions.
- **Before committing:** every change must build (`ninja -C build`). Keep the README in
  sync, including the live screen tables and the common-changes table.
- **Testing:** the owner tests on hardware. Say clearly what was only built and not run.
  Ask them for the status line (`values/s`) or logs instead of guessing.

## Porting Esp32_monitor features (started 2026-11-14)

The owner wants Esp32_monitor's design and features (`~/git/Esp32_monitor`, its
`CLAUDE.md` and `README.md` explain them) in this project. Decided with the owner:
- **UI:** Esp32_monitor's dark sidebar layout + status line for ALL pages: Home, OBD,
  CAN, Wi-Fi, BLE, IO, Display. Today's Settings / System / Read DTCs / Select Params
  move into those pages. Drive / Race / Tune stay full-screen (opened from OBD).
- **IO page:** the 5" board has no free ADC pin (GPIO6 = RTC interrupt). Only DI0/DI1
  (CH422G EXIO0 / EXIO5, isolated 5-36 V), DO0/DO1 (CH422G OC0 / OC1, open drain),
  I2C scan of the terminal's SDA/SCL, chip temperature.
- **CAN monitor** alongside OBD: ID table, rates, bus load, log; listen-only only while
  OBD is disconnected.
- No GPS / route / ride / web file manager ("this is it for now").

Steps, each built, committed and tested on the board by the owner before the next:
1. **Done, boots on the board (2026-11-14):** memory settings + `wifi_svc` + `ble_svc` +
   PCF85063 RTC (`board/rtc_pcf85063.c`), init order from Esp32_monitor, `log_heap`
   after every step. Internal free / largest block: board 195/128 KB, display 156/112,
   obd 132/92, wifi 75/36, ble **38/27 KB**. Then moved the datalog queue (~12 KB) and
   the comsm stack (4 KB) to PSRAM (not run yet). Still to hear: FPS (LVGL mallocs now
   go to PSRAM: `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`). Watch internal RAM in every
   later step; Wi-Fi scan/connect and the SD mount also take some at runtime.
2. **Done, built, not run yet:** sidebar UI. `tools/obd_ui.py` (builder from
   Esp32_monitor's eez_scaffold) writes the menu pages into the existing project:
   home, obd, readDTC, select_params, freezFrame, can, wifi, ble, io, display; removes
   startup / clearDTC / settings / system; leaves drive / liveData / tune alone.
   Bridge: `uivar.c`, `nav.c`, `screen.c`, `view_wifi.c`, `view_ble.c` copied;
   `hmi.c`, `view_sys.c`, `view_obd.c` (replaces settings_view.c), `actions.c` new;
   readDTC / freezFrame / select_params keep their names and identifiers so
   diag_view / pid_select_view still work. The project keeps EEZ's light theme
   (the Race page's original gauges rely on it); new widgets set their colours.
3. **Done, built, not run yet** (Wi-Fi + BLE pages and SNTP -> RTC already worked in
   step 2's test, 47 KB internal RAM after BLE): log files named
   `<prefix>_YYYYMMDD_HHMMSS` (local time) and stamped in Unix time once the clock is
   set, numbered + seconds since boot before; time base fixed per file at open. DTC
   reports dated too. IO sidebar icon fixed (U+F0C1 is not in LVGL's fonts: only
   LV_SYMBOL_* glyphs exist). LVGL FPS / CPU overlay removed (owner: misleading).
4. **Done, built, not run yet:** CAN page bus monitor. `can_if` now based on
   Esp32_monitor's (start / restart with bitrate + listen-only, node lock, TEC/REC),
   plus two monitor slots (`CAN_IF_MON_LOG` datalog, `CAN_IF_MON_VIEW` canmon) and
   "accept all IDs" owners (`CAN_IF_ALL_LOG`, `CAN_IF_ALL_MONITOR`); the wanted filter
   survives a restart. `canmon` = the monitor part of Esp32_monitor's canmon (no
   logger: datalog stays the only logger). Bitrate (stored) / listen-only (not stored)
   only change while OBD is idle; Connect leaves listen-only first. ID table in
   `unscii_8` (objects.can_id_table).
5. **Done, built, not run yet:** IO page + `io_svc`. CH422G datasheet (WCH CH422DS1):
   IO_OE is ONE bit for all IO0-7, and RD-IO returns pin levels only with IO_OE = 0.
   So `ch422g_read_io()` (board/i2c_io.c) holds the SD card's SPI bus
   (`waveshare_sd_bus_lock`, a dummy SPI device; sdspi takes the bus per command),
   sets IO_OE = 0, reads, restores outputs: ~0.3 ms with SD CS / LCD reset / touch
   reset / backlight enable floating on the weak pull-up. DI read only while the IO
   page is open (100 ms). DI active = line low (PC814 pulls EXIO0 / EXIO5 down;
   4.7k pull-up). DO = OC0 / OC1 via `ch422g_write_oc()`, low = on; OC written high at
   init. Ask the owner to watch for display / SD glitches with the IO page open while
   logging.
6. **Done, built, not run yet (owner's follow-up):** `web_svc` = Esp32_monitor's file
   manager, cut down to the log files in the card root (`can_` `par_` `evt_` `dtc_`
   prefixes only): list / download / delete, multi-select delete, no upload. Files
   open in datalog (`datalog_is_open()`, evt name now in the status) can't be deleted.
   httpd on core 0, priority 2 (below datalog), stack in PSRAM. Page JS checked with
   headless chromium against a mock API (never name a JS function `all`: inline
   handlers resolve it to `document.all`). Wi-Fi: with auto connect (setting
   `wifi_autoconnect`, applied live via `wifi_svc_set_auto_retry`) the station keeps
   trying every 30 s after the 5 quick retries; manual Disconnect / Forget stops it.

`sdkconfig` (local) got the step 1 options by hand; the previous copy is not kept.

## Roadmap (agreed 2026-11-14, owner: "structure it and don't forget")

Same process as the port: one step at a time, it builds, gets committed, the owner tests it
on the board/car before the next step. Order decided by the owner: **link layer first**,
the Dash UI later. Dash and Diag pages already exist in the sidebar as placeholders
(`page_dash` / `page_diag` in tools/obd_ui.py, text only).

**A. Car link layer: BLE ELM327 adapter as a standard input next to the board CAN**
Goal: OBD (comsm), CAN logging (datalog) and later Diag can use either the board's CAN 2.0
(TWAI) or a BLE ELM327 adapter, chosen by a setting.
- Owner's adapter: Vgate iCar Pro 2S, advertises as `IOS-Vlink`, pairs fine (encrypted, no
  passkey). Serial port = service `e7810a71-73ae-499d-8c15-faa9aef0c3f2`, characteristic
  `bef8d6c9-9c21-4c9e-b632-bd58c1009f9f` (R W w N I, value handle 28 on this unit; CCCD
  presumably 29). Fallback layout used by other adapters: service `0x18F0`, notify `0x2AF0`,
  write `0x2AF1`. Leave `0xFF12` (FF14/FF15, vendor, likely firmware update) alone. Look
  characteristics up by UUID, never by handle.
- ESP32-S3 = BLE only: Classic-Bluetooth ELM327 adapters can't be supported.
- ELM327 set-up: `ATZ ATE0 ATL0 ATS0 ATH1 ATSP6`; per ECU `ATSH <tx>` + `ATCRA <rx>`; request
  as hex text, reply in notification chunks until the `>` prompt. The adapter does ISO-TP.
- Limits to keep in mind: ~10-30 requests/s over BLE (slower than the board CAN); `ATMA`
  (monitor all) overflows on a busy bus, so the CAN monitor / Dash stay on the board CAN,
  and "CAN logging over BLE" can only log our own requests and replies; VW TP2.0 only with
  raw frames (tight timing); KWP1281 not possible with ELM327.
- Adds K-line (ISO 9141 / KWP2000) and J1850 for older cars.
- **A1 done, built, not run yet:** `ble_svc_serial_*()` (ble_svc.c "serial port": picks
  Vgate bef8d6c9 > 18F0 (2AF1 write / 2AF0 notify) > FFE1, finds the CCCD, notify on, RX in
  a 4 KB PSRAM stream buffer, writes split to MTU-3, MTU exchange at connect). Console:
  sub-page `ble_console` (BLE page button "Adapter console"), view_elm.c, ATZ / ATI / ATRV /
  0100 / custom command, last 19 lines.
- **A1 tested OK** (2026-11-14): ATZ -> ELM327 v2.3, ATRV 11.7V, 0100 -> 41 00 9E 3F 80 03
  from the simulator (bench: ECUs need KL15; the adapter itself only needs pin 16).
- **A2 tested OK on the bench (2026-11-14):** connect, discovery, running over the 2S. obd_client has two links (`obd_client_set_link`,
  OBD_LINK_CAN / OBD_LINK_ELM); `obd_elm.c` = ELM327 backend (set-up ATZ ATE0 ATL0 ATS0
  ATH1 ATSP6 ATAT1 on first use, ATSH / ATCRA only on change, frames reassembled from the
  header lines, result reported only at the '>' prompt, NO DATA = timeout, abort sends CR
  and waits for the prompt). obd stays BLE-free: main passes `obd_elm_io_t` (ble_svc_serial_*).
  comsm applies `comsm_set_link()` at every connect; setting `obd_link`; OBD page "Link"
  dropdown. Console stays off the adapter while OBD runs on it and makes OBD re-init after
  any console command. Not yet: raw CAN log of the ELM conversation (A3), speed tuning
  (response-count digit / ATST), auto-connect of the adapter (A4).
- Steps: A1 GATT client in ble_svc (find serial char, notify on, write, RX buffer) + a raw
  ELM test on the BLE page (ATZ, ATI, 0100); A2 `car_link` interface (request/response with
  tx/rx IDs, timeouts) with two backends, board CAN (obd_client / isotp) and ELM327; comsm
  uses it; A3 setting + UI (OBD page: link = board CAN / BLE adapter), datalog logs the
  conversation from either link; A4 auto-reconnect to the bonded adapter.

**B. Dash page: custom dash from a DBC (rusEFI first)**
- rusEFI broadcasts on CAN (base ID 512 = the removed `rusefi_base_id` setting), decoded
  with its DBC. Listen only, board CAN only (see A limits).
- The PC tool converts `.dbc` -> compact signal file on the SD card (ID, start bit, length,
  byte order, sign, scale, offset, unit, name); the dash only parses that.
- Tile layout + alarm limits in `/sdcard/db/dash/layout.json`, edited in the PC tool.

**C. Diag page: manufacturer diagnostics over UDS (VW group, Mercedes first)**
- UDS (ISO 14229) over ISO-TP, CAN first; a `uds_client` beside obd_client (NRC 0x78
  response pending, P2* up to 5 s), OBD polling paused during a job; runs over either link (A).
- Read only: ECU scan (`3E 00` to every address in the DB), identification (`22` F187 part
  number, F189 SW version, F190 VIN, F18C serial, F197 system name), DTCs `19 02 FF` with
  status, clear `14 FF FF FF` with confirmation, read data by ID `22 xx xx`. NO 2E writes,
  27 security access, 31 routines, coding.
- Later: KWP2000 for older Mercedes (ISO-TP), maybe VW TP2.0.

**D. Database on the SD card + PC tool**
- `/sdcard/db/`: `manifest.json` (version, files, checksums), `ecus/<make>.json` (name,
  address, request/response CAN ID, protocol), `dtc/<make>_<ecu>.tsv` (code, text),
  `did/<make>_<ecu>.json` (name, type, scale, offset, unit, enum), `dbc/*.sig`,
  `dash/layout.json`. Loaded per ECU into PSRAM.
- Sources: open data only (SAE generic DTCs, standard UDS DIDs, opendbc (MIT), rusEFI DBC,
  own findings). Never ship or import ODIS / Xentry databases (proprietary).
- PC tool (Python + Tk): edit tables, import DBC / CSV, validate, export; deploy over Wi-Fi
  to the dash IP (needs an upload endpoint for /sdcard/db in web_svc); live console: send a
  UDS request through the dash (`POST /api/uds`), see the reply, save the decoding into the
  DB. Needs a PIN shown on the dash, and the dash only forwards the read-only services.

**Built but NOT yet verified on hardware** (ask the owner how they went):
- **Car fix, most important** (`7434030`). The first car logs (2026-11-11) showed the
  real ECU answering in ~10 ms, but the dash had hundreds of 150 ms timeouts and
  3.29 s gaps (8 timeouts + 2 s reconnect delay); each reconnect started a new `par_`
  file and dropped the gauges.
  - Cause: on ESP32-S3 (TWAI v1) `fail_retry_cnt != -1` means single shot, so our
    0x7E0/0x7DF frames were dropped whenever they lost arbitration to car traffic.
  - Fix: software retries in `can_tx_task` (16 attempts / 20 ms).
  - Next drive: `evt_NNN.txt` should show `+tx_failed` at 0 and the connection
    staying `running`; one `par_` file per drive.
- **All traffic** (`940a919`, Settings next to Log CAN RAW; replaced Kconfig
  `CAN_ACCEPT_ALL`): opens the hardware filter while a raw log is written
  (`can_if_set_accept_all`, applied in the TX task via disable / filter / enable).
  Never run on a busy bus: watch `+log_dropped` in `evt_NNN.txt`.
- **Multi-PID requests** (`4d0ff78`, `352fdae`). The simulator answers them (6 PIDs in a
  3-frame reply) but spaces frames ~150 ms apart. That broke the 150 ms response
  timeout and ISO-TP's 100 ms N_Cr, so the dash fell back to 1 PID.
  - Fixed: N_Cr is 1000 ms (ISO 15765-2), and the deadline is extended on every frame
    of a multi-frame reply. Not re-tested yet, neither on the bench nor in the car.
  - If the System screen says "ECU accepts 1 PID per request", get a raw log.
- **Slow PIDs keep their 2 s period** (`385fdc5`): should stop the `--` flicker on the
  coolant tile.
- **Needle animation** (`596b450`) and its System checkbox.
- **Brightness** (`brightness.c`): software dimming layer by default. Optional backlight
  PWM via `CONFIG_BACKLIGHT_PWM_GPIO` after a hardware mod (dimming pad by R11/C11,
  inverted duty); derived from the schematic, never run.
- **Bus load:** the owner measured ~50 % CAN bus load, source unclear (our own traffic
  is a few percent). A raw log with All traffic would show it.
- **FPS:** ~40 % CPU and 15 FPS with logging on, before the optimisations; not
